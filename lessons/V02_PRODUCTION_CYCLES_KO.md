## 사이클 요약

여기서 “실행 시도”는 실제 Codex CLI 프로세스 수다. “빌더 후속 제품 수정”은
채택된 executor 결과를 받은 뒤 빌더가 고객 기능 또는 데이터에 직접 가한
수정 횟수다. 테스트·원장·실행기 결함 수정은 제품 수정과 섞지 않는다.

## 관찰된 교훈

1. 수용 테스트 명령은 sparse worktree에 실제로 보이는 경로만 요구해야 한다.
   사이클 2 첫 실행은 제품 변경이 아니라 범위 밖 문서와 고객 B fixture를
   요구한 명령 때문에 실패했다.
2. Git 출력은 Windows 기본 locale이 아니라 UTF-8로 명시적으로 읽어야 한글
   diff를 `CAPTURED_AT_EXECUTION` Evidence로 보존할 수 있다.
3. 토큰 상한은 사후 채택 관문이다. 사이클 2 두 번째 실행은 테스트와 증거
   캡처에 성공했어도 6,569토큰 초과로 거부됐다.
4. 같은 sparse 범위에서도 지시문을 한 파일·한 테스트 node로 제한한 채택
   실행은 100,188토큰이었다. 이는 관찰값이며 지시문 단축만의 인과 효과로
   단정하지 않는다.
5. 평가 사례 변경은 기존 승인 파일을 덮어쓰지 않고 새 버전 경로와 새
   SHA-256으로 승인받아야 한다. 사이클 3에서 기존 13건 Approval이 새 14건
   spec에 대해 거부되는 것을 원장에서 확인했다.
6. 사이클 2와 3의 채택 결과는 실행자가 만든 diff를 그대로 반영했으며 빌더의
   후속 제품 수정은 없었다. 이 경계는 각 Run의 재현성 Evidence와 Git commit으로
   검증할 수 있다.
