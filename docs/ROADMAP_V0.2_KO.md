# AI Company OS V0.2 방향과 구현 순서

## 지향점

회사의 장기 자산은 특정 모델이나 “똑똑한 에이전트”가 아니라, 같은 종류의
요청을 같은 품질로 반복 생산하는 **검증된 생산 라인(레시피)**이다. 모델과
실행 도구는 교체 가능한 부품으로 두고, 작업지시서·근거·승인·실패 교훈·통과한
레시피는 회사 자산으로 남긴다.

CEO는 원칙적으로 작업지시서 승인과 최종 납품 승인에만 개입한다. CTO, CPO,
CMO는 독립 의견을 내고, 합의문보다 충돌 지점을 CEO에게 올린다.

## 시스템 경계

- **Codex 로컬 프로젝트**: CEO가 코딩 업무를 말하고 결과를 검토하는 주 작업실
- **AI Company OS**: WorkOrder, Evidence, Event, 승인 상태의 유일한 공식 원장
- **ExecutorPort 뒤 실행자**: 한 WorkOrder를 실제로 수행하는 교체 가능한 직원
- **저장소 스킬**: 통과한 업무 방식을 재사용하는 레시피
- **Claude Opus handoff**: 생산자와 분리된 수동 독립 검수
- **OpenClaw**: 로컬 생산 루프가 안정된 뒤 붙일 선택적 대화 입구

GitHub 보드, Langfuse, Graphiti 같은 도구는 SQLite의 결정·승인 상태를
복제하지 않는다. 필요할 때 각각 코드 협업, 실행 관찰, 검색 보조 역할만 맡는다.

## 현재 위치 (2026-09-25)

stop/resume, Venture 문맥 분리, Evidence/Artifact hash, 소스 결속, 수동 Opus
재검토와 수리 루프가 구현됐고 전체 208개 테스트가 통과한 기준점이 있다.

## 구현 순서

### 1. 실행 기반 정비

- 장시간 executor를 SQLite 쓰기 트랜잭션 밖에서 실행
- 동시 실행은 WorkOrder의 `EXECUTING` 청구로 한 건만 허용
- 처리 가능한 실패는 이전 상태로 복구하고 Event로 기록
- 하드 프로세스 종료 뒤 남은 실행 청구를 명시적으로 복구하는 기능 추가
- 실제 외부 실행 전에 비용, 시간, CEO 시간, 재작업 횟수 상한 추가

완료 기준: 한 WorkOrder가 실행 중이어도 다른 Venture의 원장 쓰기가 막히지
않고, 실패·재시작·동시 실행 시험이 모두 통과한다.

### 2. 합성 챗봇 평가 세트

정답과 채점 근거를 알고 있는 합성 카페 FAQ 사례를 만든다. 현재 DRAFT 세트는
기존 10건, 표현 변경 2건, 가격 추측 방지 1건을 포함하며 다음을 채점한다.

- 알려진 답변에 source id가 있는가
- 자료 밖 질문을 거절하는가
- 비공개 표식을 노출하지 않는가
- 명절 휴무와 신규 메뉴 수정 요구를 반영했는가
- 실행 시간·Codex CLI 프로세스 호출·입력+출력 토큰 상한을 지켰는가

CEO가 질문·정답·금지어·threshold를 검토하기 전까지 공식 평가가 아니다.

### 3. 실제 실행자 한 명

평가 세트를 통과할 수 있는 최소 실행자 하나만 `ExecutorPort` 뒤에 연결한다.
Deep Agents는 후보이지 확정 의존성이 아니다. 채택 전에는 기존 방식과 같은
시험으로 비교하고, API 키·실고객 데이터·백그라운드 실행은 별도 승인 없이는
도입하지 않는다.

완료 기준: 한 번의 승인된 지시로 합성 챗봇 코드를 수정하고, 자동 시험,
동일 소스의 rubric Evidence, 브라우저 확인, 독립 검수를 끝낸다. 실제 LLM
답변형 제품을 만들었다고 표현하지 않고 결정형 FAQ 미리보기임을 명시한다.

### 4. 스킬 축적 루프

업무 완료 → 교훈 추출 → 스킬 변경안 → 기존 평가 재실행 → 통과 버전 채택
순서로 진행한다. 실패한 개선안도 이유와 함께 남긴다. 같은 유형의 실제 업무를
세 번 수행하기 전에는 일반 생산 라인으로 성급히 승격하지 않는다.

### 5. 필요한 도구만 단계적으로 연결

| 도구 | 도입 시점 |
|---|---|
| Agent Skills | 지금: 저장소 레시피 형식으로 사용 |
| Deep Agents | 평가 세트 뒤 실행자 후보 비교 |
| Docling | PDF/PPT/RFP 업무가 첫 라인에 실제로 필요할 때 |
| Langfuse | SQLite 기본 실행 기록만으로 병목 분석이 어려워질 때 |
| Graphiti | 확정 결정 수십 건을 검색할 필요가 생길 때, 검색 보조로만 사용 |
| Browser Use | 웹 직접 조작이 검색보다 명확히 이득인 시험이 생길 때 |
| OpenSandbox | 신뢰 경계가 다른 여러 Venture를 동시에 실행할 때 |
| DSPy/GEPA | 충분한 평가 사례가 쌓인 뒤 개선 후보 생성에만 사용 |
| OpenClaw | 로컬 지시→실행→검수 루프가 안정된 뒤 대화 입구로 연결 |

### V0.7 비용 사전 제한 backlog

현재 토큰 상한은 Codex CLI가 끝난 뒤 사용량을 읽어 초과 결과의 **채택을
거부**한다. 따라서 원장과 제품은 보호하지만 이미 발생한 토큰 소비를 막지는
못한다. V0.7에서는 실행 전 최대 turn 수와 입력 context 예산을 작업지시서에
결속하고, 지원되는 CLI 제어가 확인되면 실행 중 취소를 더해 초과 실행 자체를
줄인다. 이 기능 전까지 `token_limit`을 사전 지출 제한이라고 표현하지 않는다.
